# review-brief

一轮修改收尾时，把「为什么改、改了什么、怎么审」沉淀成一份自包含的审查简报，交给另一个没有本对话上下文的 agent 独立复查。

整个 skill 只有一条铁律：**审查方读不到你的对话历史**。简报里没写的，审查方就不知道。需求原话、变更边界、验证方法，宁可多写一句，不能让审查方靠猜。

## 触发场景

| 场景 | 特征 | 需求从哪来 |
| --- | --- | --- |
| A. 刚改完（同会话） | 本对话刚完成一轮修改或修复 | 从对话历史提取，基本不用提问 |
| B. 新会话补生成 | 用户带着某个提交或工作区来找你 | 对话里没有需求，先问用户要 |

判断不出是哪种就直接问一句："需求是在这个对话里提的，还是之前在别的会话里？"

## Procedure

### Step 1 — 沉淀需求

**场景 A**（从对话历史提取，不要凭印象转述）：

- **原始需求**：用户原话逐字引用（blockquote）。分多次说的按时间合并；中途改过主意的保留演变（"最初要 X，后确认为 Y"——审查方需要知道代码为什么长这样）
- **澄清与追加约束**：讨论中确认的细节、被否掉的方案（"不要用 XX 方式实现"也是约束）
- **验收标准**：怎么算做完。用户说过的直接引；用户没说的，从需求推导可观察、可验证的条目，**每条标注"⚠ agent 整理，用户未明确"**——这批条目正是审查方最该帮忙盯的

**场景 B**（先问再写）：问用户要需求描述或 issue / 工单链接，以及当时是否约定过验收标准。**不要根据代码反推需求再冒充原始需求**——反推内容只能作为推断写并标注。

### Step 2 — 圈定变更范围

先跑只读命令摸清状态（全程只读，不改任何东西）：

```bash
git status --porcelain     # 未提交改动 + 未跟踪文件
git log --oneline -15      # 近期提交
git branch --show-current  # 当前分支
```

按状态三分支：

| 状态 | 范围口径 | 简报里写什么 |
| --- | --- | --- |
| 全部未提交 | 工作区 vs HEAD | `git status` 摘要 + `git diff HEAD --stat`；**必须提醒**：untracked 新文件不进 `git diff`，审查方要用 `git status` 找全 |
| 全部已提交 | `<base>..<head>` 提交区间 | 逐提交清单（hash + message + 日期）+ 整体 diff 命令 |
| 混合 | 两段都收 | 分开写清，各自给命令，不要混在一起 |

已提交时，确定"本次"提交集合的依据按优先级取：

1. 对话历史里有明确记录（本会话亲手提交了哪几笔）→ 直接用
2. 用户指定（"最近 3 个提交"、"abc1234 之后的所有提交"）→ 按用户说的
3. 按 message 与时间推断 → **列出候选让用户确认，绝不静默猜**。提交边界搞错，后面整个审查都在做无用功

base 取第一个相关提交的父提交（`<hash>^`），简报里显式写出 base 和 head。

非 git 目录：跳过 git 命令，从对话历史手工列改动文件，简报里注明"非 git 仓库，无 diff"，审查依据只剩文件清单 + 关键改动摘录。

### Step 3 — 逐文件整理变更清单

对每个变更文件搞清三件事：改了什么、为什么改、怎么验证没改坏。产出两样：

**文件清单表**（放简报 §2.3）：

| 文件 | 变更 | 意图 |
| --- | --- | --- |
| src/auth.ts | 修改 | 登录接口加验证码校验（对应验收标准 2） |

**关键改动摘录**（放简报 §2.4）：挑 3-5 个最要紧的 hunk 原文贴出（带 file:line），其余不贴，全量 diff 让审查方用命令自取：

```bash
git diff <base>..<head>              # 整体 diff
git show <hash>                      # 单个提交
git diff <base>..<head> -- <file>    # 单文件
```

diff 合计超过约 500 行时摘录更要克制：只贴"不看就没法判断是否符合需求"的部分，其余靠命令，并在局限性一节注明。

### Step 4 — 拟审查要点（三维度）

简报的智力核心。**每条都要针对本次改动，带 file:line 或具体验证方法**；"注意边界条件"这类通用空话一条都不要写。

**① 需求符合性**：逐条验收标准列表格（验收标准 → 对应改动 → 怎么验证）。另列**范围外改动**小节：本次顺手做了但需求没要求的（顺手重构、格式化、修了别的 bug），如实列出让审查方裁决是保留还是拆走——藏着掖着，被发现一次，整份简报的信任就没了。

**② 潜在 bug / 风险点**：

- **自己拿不准的点优先写**：改动时心里发虚的地方（"过期判断和校验的先后顺序好像不对，没测"）是简报里最值钱的内容，如实写、标位置、说不确定的理由
- 再按改动类型过一遍：边界与空值、错误处理、类型转换、并发 / 时序、硬编码值、调试代码与 console.log 残留——只在真的碰到时列
- 每条带 `<file:line>`，能写复现方法就写

**③ 影响面**：

- 调用方：被改的函数 / 组件 / 接口还有谁在用——**真的去 grep，把结果写进简报**，不要只写"已检查无影响"
- 波及：共享状态、对外接口、配置项、依赖版本动了没有；动了谁受影响
- 同步项：测试要不要补、文档要不要改、生成物 / 锁文件要不要重跑（每个项目有自己的对应物）
- 建议回归：最小回归集——必须过一遍的功能点、必须跑的测试命令

### Step 5 — 写入并报告

- 位置：`<仓库根>/review-briefs/YYYY-MM-DD-<slug>.md`（slug 取需求关键词的短横线英文或拼音）；用户指定路径则用用户的；同名文件已存在就追加 `-HHMM` 后缀，**不覆盖**
- 语言跟随用户（默认中文）
- **不动 .gitignore**：简报是一次性交接物，进不进版本库由用户决定，报告里提一句即可
- 报告：文件路径 + 一句用法（"把这个文件发给另一个 agent，它会按文档开头的指引开始审查"）

### Step 6 — 自检

- [ ] 需求原话逐字引用了；所有非原话内容都标了"agent 整理 / 推断"
- [ ] 提交范围有明确依据（对话记录或用户确认过），不是猜的
- [ ] 每个变更文件都有"改了什么 + 为什么"
- [ ] 审查要点每条都具体（file:line / 验证命令），没有通用空话
- [ ] 自己拿不准的点写了，范围外改动也列了
- [ ] **自包含**：想象把文件直接发给一个全新会话，它每一步都不需要追问——哪里会卡住，哪里就是没写够
- [ ] 给审查方的命令在当前仓库状态下都能直接复制执行

## 简报模板

按此结构写，空节写"无"不删节。各节怎么填见 Procedure 对应步骤。

````markdown
# 审查简报：<一句话标题>

> **给审查 agent**：本文档由实现方（另一个 agent 会话）生成，你是审查方，不需要其他上下文。
> 路线：§1 了解需求 → §2 查看变更 → §3 逐项审查 → 按 §4 的格式汇报结论。
> 文档本身有缺口（需求不清、范围不明）也算审查发现，一并指出。

| 项 | 值 |
| --- | --- |
| 生成时间 | 2026-10-17 14:30 |
| 仓库 / 分支 | `D:\path\to\repo` @ `main` |
| 变更状态 | 已提交 2 个提交（`abc1234^..def5678`）/ 未提交 / 混合 |
| 变更位置 | 本机工作区未推送 / 已推送 origin |
| 实现方 | <agent 名称或模型> |

## 1. 需求 / 问题

### 1.1 原始需求（用户原话）

> 逐字引用……

### 1.2 澄清与追加约束

- ……

### 1.3 验收标准

1. ……（用户原话）
2. ……（⚠ agent 整理，用户未明确）

## 2. 变更范围

### 2.1 提交记录（如有）

| # | 提交 | 说明 |
| --- | --- | --- |
| 1 | `abc1234` | fix: …… |

基线 `abc1234^`（不在本次变更内）→ `def5678`；整体 diff：`git diff abc1234^..def5678`

### 2.2 未提交变更（如有）

```text
 M src/auth.ts          （+36 −12）
?? src/auth-captcha.ts  （新增）
```

untracked 文件不进 git diff，找全变更用：`git status --porcelain`

### 2.3 文件清单与意图

| 文件 | 变更 | 意图（为什么改） |
| --- | --- | --- |

### 2.4 关键改动摘录

（3-5 个 hunk 原文，带 file:line，每段一句"为什么贴这段"）

## 3. 审查要点

### 3.1 需求符合性

| 验收标准 | 对应改动 | 怎么验证 |
| --- | --- | --- |

**范围外改动**：……（需求没要求但本次做了的；无则写"无"）

### 3.2 潜在 bug / 风险点

1. `src/auth.ts:88`：过期判断在校验之后，过期验证码可能仍通过——**实现方自评：拿不准，没测过**，请重点验证
2. ……

### 3.3 影响面

- **调用方**：……（grep 结果，带文件与行号）
- **需要同步**：测试 / 文档 / 配置 / 生成物
- **建议回归**：最小回归集 + 测试命令

### 3.4 建议审查步骤

1. `git diff abc1234^..def5678` 通读全量 diff（约 150 行）
2. 对照 §3.1 逐条验证需求
3. 重点看 §3.2 风险点
4. 跑 `npm test`；手动过一遍登录主流程

## 4. 输出要求

- 按三档汇报，每条带 `file:line` 与理由：**阻塞**（不符合需求 / 确定 bug / 破坏其他模块）、**建议**（不阻塞的改进）、**疑问**（拿不准，向实现方求证）
- 逐条回答验收标准：通过 / 不通过 / 无法验证

## 简报局限性

（如实写，如"需求为用户事后口述，非原始记录"；无则删本节）
````

## Output contract

- 产出 `<仓库根>/review-briefs/YYYY-MM-DD-<slug>.md`，模板各节齐全（空节写"无"，不删节）
- 全程只读 git；不修改被审查仓库的任何代码与配置（.gitignore 也不动）
- 简报里的命令审查方可直接复制执行
- 结束时报告：文件路径 + 一句用法

## Failure handling

| 情况 | 处理 |
| --- | --- |
| 新会话拿不到原始需求 | 问用户要描述或 issue 链接；仍拿不到，§1.1 写"用户未提供原始需求，以下为代码反推（⚠ 不可信）"，并提示审查方先与用户对齐需求 |
| 提交集合有多个候选、推断不出 | 列候选（hash + message + 日期 + 推断依据）让用户选，不猜 |
| diff 合计很大（> 500 行） | 摘录只贴关键 hunk + 给全量命令，局限性里注明 |
| 非 git 仓库 | 手工列文件清单 + 关键改动摘录，注明无 diff |
| 混合状态（部分已提交） | 提交区间与工作区分两段写，各自给命令 |
| 需求没有验收标准 | §1.3 写 agent 整理的推断标准并逐条标注，§3.1 提示审查方重点复核 |
| 变更含敏感信息（密钥 / token / 内网地址） | 摘录里打码，标"已脱敏" |
| 同名简报文件已存在 | 追加 `-HHMM` 后缀，不覆盖 |
| 用户只要口头总结、不要文件 | 直接在回复里按模板输出，不写文件 |

## Examples

**输入（场景 A）**：同一会话里用户报了"导出 Excel 超过 1000 行就卡死"，agent 修完并提交了 2 个 commit；用户说"生成审查简报，我发给另一个 AI 复查"
**输出**：`review-briefs/2026-10-17-excel-export-freeze.md`——§1.1 逐字引用卡死描述与用户补充的复现步骤；§2.1 两笔提交 + 整体 diff 命令；§3.2 含一条实现方自评"改成流式写入后，合并单元格的处理没测过"；§4 要求逐条回答验收标准。

**输入（场景 B）**：新会话，用户说"帮我给最近的提交出一份审查简报"
**输出**：先问需求来源，拿到需求文字后 `git log` 列出近几笔作为候选让用户确认，确认后生成简报——提交边界用的是用户确认的那个。

**输入（场景 A 变体）**：改动还没提交，用户说"还没想好怎么提交，先出简报"
**输出**：§2 走"未提交变更"分支，写明 untracked 文件清单与"新文件不进 git diff"的提醒。

## 与相邻技能的边界

| 想要…… | 用什么 |
| --- | --- |
| 同一会话内立刻派 subagent 审查、不经人工交接 | superpowers 的 requesting-code-review（如已安装） |
| 面向版本记录、给用户看的变更说明 | changelog-craft |
| 走 GitHub PR / GitLab MR 正式评论流程 | 对应平台的 review 能力 |
| 跨会话交接：让另一个毫无上下文的 agent 独立复查 | **review-brief**（这个 skill） |

## Windows (win32) platform notes

用到的 git 命令（status / log / diff / show / branch）全部只读、跨平台通用，Git Bash 与 PowerShell 都行；路径含空格记得加引号。写简报文件用 Write 工具，无平台差异。
